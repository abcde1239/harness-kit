# Artifact management

Use one managed run for the files generated by a work item. Create it only when you need to retain a report, log, screenshot, trace, or similar output. Share the returned path with the agents working on the same item and give each writer its own filenames or subdirectory. Keep only the files needed to understand or reproduce the result. Put reusable scripts, executable tests, and fixtures in their normal project locations.

| Location | What belongs there |
|---|---|
| `.harness/` | Harness state such as plans, tasks, validation summaries, and publication review records |
| `artifacts/runs/<id>/` | Temporary evidence from one work item, with a CLI-owned `run.json` |
| `artifacts/releases/`, `artifacts/distribution/`, `artifacts/skill/`, `artifacts/snapshots/` | Versioned deliverables, packaged Skills, and reviewed exports with a separate retention policy |
| `artifacts/archive/` | Historical outputs kept for reference |
| `docs/verification/` | Maintained verification instructions and durable summaries |

```sh
harness artifacts create checkout-e2e --json
harness artifacts finish <id>
harness artifacts keep <id>
harness artifacts clean
harness artifacts clean --yes
```

Use the `id` and project-relative `path` returned by `create`. Prefer names such as `browser/checkout.png` or `tests/results.json` inside that run. Pass the directory to the existing runner when it supports an output path. Keep framework outputs such as coverage in their configured locations. When all writers have stopped, mark the run finished. Pin runs you rely on for durable evidence using `keep`. Use `release` to remove the pin when it is no longer needed.

## Design and review outputs

Allocate the run before generating a design draft. Put editable mockups, throwaway HTML prototypes, export variants, and review screenshots in a `design/` subdirectory of that run. Keep accepted specifications and decisions in the project’s documentation, and place maintained diagrams or site assets in its existing asset directories.

`check` and `run` report `documents.artifacts` for common native design formats and recognizable draft names in root or workspace `docs/` directories. Add an exact file path to `documents.artifactAllowlist` for a maintained asset flagged by the rule. The check uses names and formats; it cannot establish the purpose of a generic filename. Review misplaced files, update their references, and move temporary outputs into a run. `artifacts clean` does not scan or delete files in `docs/`.

## Retention and cleanup

Set `"artifacts": { "retentionDays": 14 }` in `harness.config.json` to customize the default 14-day window. Age is measured from the later of completion and the most recent file or directory modification. `clean` previews the status of each entry under `artifacts/runs/`. With `--yes`, it removes expired, finished runs with valid registration. It skips active or pinned runs, runs referenced by `.harness/tasks/` records, Git-indexed paths, and trees containing links, special files, or Git metadata. Legacy and archive directories are outside cleanup scope. Use an explicit pin for references in other locations, such as a Markdown report or an issue. Routine `check` and `run` never clean files.

`check` reports unexpected files in `.harness/` as `storage.state` errors. Store a custom JSON state export under `.harness/tmp/`, or put a generated report in a managed run. `artifacts.layout` warns about loose or uncategorized root outputs and unregistered runs. You can make it an error once the old layout has been reviewed. `tests.artifacts` reports recognized test files in managed runs even if the broader artifact directory is excluded from normal test layout checks.

Harness keeps `.harness/` state available for its commands. Artifact expiry never removes task, verification, or hook state. Manage temporary Hook snapshots separately with `harness hooks clean` as described in the [project layout](./project-layout.md). Check existing Git ignore rules for local outputs and state.

For migration, preview first, then review legacy directories by purpose. Keep authoritative builds and acceptance evidence with the corresponding version or task. Use the new layout for subsequent work. Inspect nested checkouts and unknown folders individually before moving or deleting them. Clearing the managed run area never requires moving old files into it.
